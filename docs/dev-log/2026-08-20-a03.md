### 小决策

**问题**：file address 是否做路径校验？

**决策**：不做路径校验。

## 设计决策

### D1. AddressError 独立错误类

```typescript
export class AddressError extends Error {
  constructor(message: string) {
    super(message)
    this.name = 'AddressError'
  }
}
```

**理由**：
- 调用方可以用 `instanceof AddressError` 精确捕获
- 与未来的 `OpError`、`L3Error` 等区分
- 错误信息包含原始 message，便于调试

### D2. writeAddress to literal 抛错（而非 silent fail）

**理由**：
- 显式失败帮助发现编程错误
- silent fail 会导致难以追踪的 bug
- 这是设计层面的约束：literal 是只读的

### D3. writeAddress to file 通过 String() 转换

```typescript
await fs.writeFile(addr.path, String(value))
```

**理由**：
- 文件内容必须是字符串
- 自动转换简化调用方
- 复杂对象需要调用方先 JSON.stringify

### D4. 不做变量名格式校验

**理由**：
- A3 阶段简化，只做基础读写
- 格式校验（如 `$` 前缀强制）留给后续
- 测试覆盖了 "literal 不读 resultStore" 强调这是简化

## 反思与收获

### 收获 1：Address 解析器是 move 模式的基础

现在可以独立测试：
```typescript
const value = await resolveAddress(from, state)
await writeAddress(to, value, state)
```

这就是 move primitive 的核心逻辑。A4（move primitive）可以直接调用这两个函数。

### 收获 2：真实 fs 测试的价值

虽然麻烦（要管理 fixtures 目录），但 file address 涉及真实 IO，必须真实测试。
mock file IO 无法发现编码问题、权限问题等真实场景。

### 收获 3：集成测试（move 模式）验证完整流程

测试覆盖了：
- literal → variable
- variable → file
- file → variable

这些是 move 的所有组合，确认 Address 解析层无问题。

### 收获 4：AddressError 命名一致性

之前在计划中用过 `OpError`、`L3Error` 等，Address 解析器对应 `AddressError`。
**收获**：错误类命名应该与模块对应。
