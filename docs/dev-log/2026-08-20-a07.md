## 目标

实现 `execute_op` primitive —— **L1 与 L2 的真正集成点**：

1. 从 `internalStore` 读取所有 inputs（每个 input 必须是 internal kind）
2. 通过 `state.l2.get(operation)` 查找 op
3. 调用 `op.execute(resolvedInputs)`
4. 把 outputs 写入 `internalStore`（每个 output 必须是 internal kind）
5. 已知错误（`OperationError` 对象）作为 outputs.error 正常写入
6. 硬错误（throw）向上抛给 L1 主循环处理（propagateHardError）

## 设计决策

### D-A7-1: inputs/outputs 运行时校验 internal

**决策**：execute_op 在运行时验证每个 input/output Address.kind === 'internal'，违规抛 `ExecuteOpError`。

**理由**：
- L1 调度器只识别寄存器地址（与 conditional_skip 一致）
- 与 doc 06 §3.2 设计意图一致
- 运行期校验防止 L3 编译器 bug 导致不一致状态

### D-A7-2: 已知错误作为数据返回，不抛错

**决策**：op 返回 `{ ..., error: OperationError }` 时，execute_op **不抛错**，而是正常写入 outputs（包括 error 字段）。

**理由**：
- 与 doc 06 §3.2 / doc 10 §三.3 设计一致
- DAG 条件分支通过 `conditional_skip(conditionAddr: $r_err)` 检查错误
- 抛错会中断 DAG 流，无法实现条件分支

### D-A7-3: 硬错误向上传播，不在 execute_op 中 catch

**决策**：op throw 时，executeOp 让错误向上抛（不 catch）。

**理由**：
- L1 main loop 的 switch dispatch 有 try/catch，专门处理硬错误（doc 10 §三.3）
- propagateHardError 在那里调用，根据 parent intent 决定如何向上传播
- execute_op 本身不应该处理硬错误（不是它的职责）

### D-A7-4: $r_err last-wins 语义

**决策**：多次 op 调用写入同一个 `$r_err` 时，最后一次写入覆盖之前。

**理由**：
- 这是"全局错误寄存器"的自然语义
- DAG 中通常每次循环只看最近的错误
- 实现简单：直接用 Map.set（已支持覆盖）

### D-A7-5: entry.status 状态机（pending → running → done）

**决策**：
- pending → running（execute_op 开始时设置）
- running → done（成功完成）
- running（保持，硬错误时未到 done 设置）

**理由**：
- 提供 entry 执行进度的可观察性
- 调试和 trace 用
- 硬错误时 status 保持 running，让上游（main loop 的 propagateHardError）能区分

### 关键代码

```typescript
export async function executeOp(
  entry: OpEntry,
  state: ExecutionState
): Promise<void> {
  // 1. 查找 op
  const op = state.l2.get(entry.operation)
  if (!op) {
    throw new ExecuteOpError(`Operation '${entry.operation}' not registered`)
  }

  // 2. 校验 outputs 是 internal（inputs 在 resolveInputs 中检查）
  validateOutputs(entry.outputs)

  // 3. 标记 running
  entry.status = 'running'

  // 4. 解析 inputs（从 internalStore）
  const resolvedInputs = await resolveInputs(entry.inputs, state)

  // 5. 调用 op（硬错误会 throw，让外层 catch 处理）
  const outputs = await op.execute(resolvedInputs)

  // 6. 写入 outputs 到 internalStore
  for (const [name, addr] of Object.entries(entry.outputs)) {
    await writeAddress(addr, outputs[name], state)
  }

  // 7. 完成
  entry.status = 'done'
  state.stack.pop()
}
```

### Mock L2 增强

```typescript
// 新增可编程 mock 工厂
export function createProgrammableOp(
  config: ProgrammableMockConfig,
  tracker: MockOpTracker
): Operation {
  return {
    name: config.name,
    formalSpec: config.formalSpec,
    execute: async (inputs) => {
      tracker.record(config.name, inputs)
      switch (config.behavior.kind) {
        case 'return':
          return config.behavior.outputs
        case 'returnError':
          return { error: { code, message, op, timestamp } }
        case 'throw':
          throw config.behavior.error
      }
    }
  }
}
```

支持的 mock 行为：
- `return`: 返回成功结果
- `returnError`: 返回标准 OperationError
- `throw`: 抛出任意 Error

## 反思与发现

### R1: execute_op 是 L1 与 L2 的真正集成点

A7 之前的所有 primitive（move, skip_n, conditional_skip）都是 L1 内部操作。A7 第一次让 L1 调用 L2，验证了：
1. L2 Registry 接口设计正确
2. formalSpec 元数据被正确使用
3. 双区架构约束在 execute_op 层正确生效
4. 已知错误 vs 硬错误的处理边界正确

### R2: entry.status 在硬错误时保持 running

**意外发现**：原计划是 hard error 时 status = 'error'，但当前实现是 status = 'running'（因为 catch 块不存在，硬错误直接 throw）。

**评估**：
- ✅ 优点：让 main loop 的 propagateHardError 能区分（'error' 是新状态，'running' 是异常中）
- ❌ 缺点：可能让调试者困惑"为什么 entry 一直 running？"

**决定**：保持 'running'，但增加注释说明。这是设计权衡，不影响功能。

### R3: 可编程 mock 是 A7+ 测试基础设施

A5/A6 测试用的是固定 mock（A5 用 throwing_op 抛错、A6 不依赖 mock）。

A7 测试需要：
- 自定义返回值（多 inputs / 多 outputs）
- 自定义错误返回（OperationError）
- 自定义 throw（自定义 Error message）

**createProgrammableOp** 工厂满足这些需求。可复用于 A8（execute_intent）和 B/C 阶段。

### R4: 与 move 的真实集成点验证

之前 A4（move）和 A7 是分开的测试。A7 测试验证：
- literal → move → internal → execute_op → output → 下轮 op input
- 这是 Phase B 真实 L2 ops 的标准流程
- 双区架构在数据流中是正确的
