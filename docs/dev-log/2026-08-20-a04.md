### 1. 创建 src/l1/primitives/move.ts

**核心函数**（仅 4 行实现）：

```typescript
export async function executeMove(
  entry: MoveEntry,
  state: ExecutionState
): Promise<void> {
  const value = await resolveAddress(entry.from, state)
  await writeAddress(entry.to, value, state)
  state.stack.pop()
}
```

## 设计决策

### D1. executeMove 是纯函数（除 stack 操作外）

**理由**：
- 只接受 entry 和 state，不依赖其他模块状态
- 易于测试
- 易于复用

### D2. 失败时不弹栈

**理由**：
- 错误处理需要 entry 上下文（知道哪个 move 失败）
- 弹栈是 main loop / error propagation 的责任
- 让 primitive 保持原子性

### D3. 不修改 entry 本身

**理由**：
- entry 是不可变快照
- 修改 entry 会导致调试困难
- 测试覆盖了"id、parentIntentId、createdAt 保持不变"

### D4. file → file 是"拷贝"而非"移动"

**理由**：
- 当前实现 resolve 读取 + write 写入，是拷贝行为
- 后续如果需要"移动"语义（删除源），需要专门处理
- MVP 阶段拷贝即可

## 反思与收获

### 收获 1：第一个 primitive 实际工作

之前 13 个文件都是基础设施。现在 `executeMove` 真正"做事"了。
**学习**：基础设施→primitive 实现的过渡很自然。

### 收获 2：move 的实现极其简单

只有 3 行核心代码。这是因为：
- resolveAddress 已经处理好读取（A3）
- writeAddress 已经处理好写入（A3）
- executeMove 只是组合这两个调用

**学习**：好的模块化让 primitive 实现变得简单。

### 收获 3：错误处理的"不弹栈"是关键设计

如果 move 失败时弹栈，错误处理就失去 entry 上下文。
**学习**：primitive 行为应该让上层（main loop）有足够信息做决策。

### 收获 4：25 个测试覆盖了一个"简单" primitive

虽然实现只有 3 行，但测试覆盖：
- 5 种 Address 组合
- 7 种 Value 类型
- 错误处理（含 atomic 语义）
- 多次执行场景
- 边界情况（空字符串、0）

**学习**：测试覆盖是设计的一部分，不是实现后的补充。

## 对后续 Phase 的影响

**影响 1：A5 (skip_n) 类似简单**

executeSkipN 也是 ~10 行实现。模式与 executeMove 类似。

**影响 2：executeMove 是 executeOp 的"模板"**

executeOp 需要：
1. 解析 inputs（用 resolveAddress）
2. 调用 op.execute
3. 写入 outputs（用 writeAddress）
4. 弹栈

executeMove 是 1+3+4 的简化版。

**影响 3：错误处理模式确立**

后续 primitive 错误处理都按"不弹栈、抛错向上"模式。
