## 2. 场景验证结果

### D-A 递归循环（doc 10 §6.5 落地）⭐

**两经验设计**：
- `count_to`（入口）：初始化 `$r_cur = 0` → 进入递归
- `count_up_iter`（递归）：pre 加 1 → judgment `$r_cur >= $r_input_target` → done / recurse（自嵌套）

**关键发现**：`internalStore` 全局共享使子/父经验看到同一个 `$r_cur`，
递归累积状态**无需参数传递**——优雅绕过了 D-C6-1（嵌套 params 仅 literal/input）的限制。

**验证**：
- 计数到 5 / 边界 target=1 ✓
- **性能基线（D4）：200 层递归仅 8ms**（每层 ~0.04ms）
- 深度防护：`maxRecursionDepth=10` + target=100 → `RecursionDepthError` 直接抛出
  （即使 `handleError=true` 也不被业务截获——L1 系统防御正确性实战验证）

### D-B 多经验协作

`setup_workspace` 编排经验串联 4 条核心经验：
`safe_write → write_file → replace_in_file → read_file`

- 子经验结果经全局寄存器跨经验回传（`$r_content` / `$r_count`）
- 幂等性：第二次运行 safe_write 跳过配置，其余照常

### D-C 错误恢复

恢复决策是**上层职责**（LLM/调用方），L3/L1 只负责把失败数据化：
- 探测（exists=false）→ 创建 → 重试成功
- safe_write 跳过（bytes=0）→ 业务判断 → 换 write_file 强制覆盖

## 3. 过程中修复

| 问题 | 根因 | 修复 |
|---|---|---|
| increment_counter 未注册 | 测试环境遗漏 | mkEnv 补注册 |
| `value=a` → `vblue=b` | replace_in_file 是 replace_all 语义 | 测试改用无歧义内容 |
| replace_in_file 对缺文件产生 ERR_INVALID_ARG_TYPE | 链式步骤不检查中间错误，null 传入下游 | 场景改为「先探测再恢复」（更符合业务现实）|

**设计观察**：链式经验（如 replace_in_file）中间步骤失败后会带着 null 继续走——
这是 MVP 已知取舍（步骤间无 conditional_skip 检查）。改进方向：编译器为 handleError
经验的步骤间自动插入错误检查跳转。记入遗留。
