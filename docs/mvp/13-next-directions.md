## 二、方向候选与评估

### 方向 A：接入真 LLM（L4 真模型）

**内容**：把 `MockL4.recognize` 替换为真模型调用（接口形状已一致）。
输入 = 用户话语 + 可用经验清单（id + description）；输出 = JSON intent。

- **价值**：★★★★★ 架构核心假设的最后一环——「LLM 只需识别意图，
  不需要知道如何执行」在真实模型下是否成立。表达刚性（差距 #5）唯一解。
- **成本**：中。需要模型 API 接入、prompt 设计、结构化输出解析、失败重试。
- **依赖**：无（接口已就绪）。
- **风险**：真模型的识别质量未知——可能暴露经验 description 写得不够好、
  或意图粒度设计问题。这恰恰是有价值的验证点。
- **前置**：建议先做 E2 的能力清单机制（已有）作为 prompt 素材。

### 方向 B：实现 Environment Context（doc 08）

**内容**：会话级持久化元数据容器（OS/项目/cwd/用户配置），跨 turn 复用，
分层访问（L4 摘要只读 / L3 读写 / L2 只读），读写可观测。

- **价值**：★★★☆☆ 多轮会话的地基。没有它，每句话都是孤立的
  （cwd 每次都要重说）。doc 08 设计已完成，实现路径清晰。
- **成本**：中。ExecutionState 扩展 + 各层访问接口 + pipeline 生命周期管理。
- **依赖**：无硬依赖；与 A 并行可。
- **风险**：低。设计已评审过。
- **注意**：与「多轮对话记忆」区分——EC 只存环境元数据，不存对话历史。

### 方向 C：经验库扩充 + 反馈演化闭环

**内容**：从真实使用提炼经验至 30-50 条；打通 feedback_history → 经验修订流程。

- **价值**：★★★☆☆ 经验库质量决定系统能力上限。但没有真实使用就没有真实反馈。
- **成本**：高（持续投入型）。
- **依赖**：**强依赖 A**（真 LLM 带来真实使用）和 B（真实使用需要会话）。
- **风险**：经验之间语义重叠/冲突需要治理机制。
- **结论**：不宜现在做，是 A/B 之后的自然阶段。

### 方向 D：健壮性补强（两个遗留）

D1 链式经验中间错误拦截：编译器为 handleError 经验的步骤间自动插入
`$r_err` 检查跳转（避免 null 下传）。
D2 嵌套 params 支持 register 引用（D-C6-1）：intent.params 支持运行时求值标记。

- **价值**：★★☆☆☆ D1 提升链式经验健壮性；D2 在全局寄存器方案
  （Phase D 已验证）覆盖了大半场景后，剩余场景有限。
- **成本**：D1 中（编译器改动 + 全量回归）；D2 中高（类型系统 + 运行时求值）。
- **结论**：D1 值得做（尤其接真 LLM 后经验会更复杂）；D2 缓行。

### 方向 E：观测性（结构化 trace）

**内容**：指令步数/寄存器轨迹/分支决策/L4 识别置信度的结构化日志。

- **价值**：★★★☆☆ 调试复杂经验和分析真 LLM 识别错误的必备设施；
  也是对外展示「CPU 取指模型」的可视化素材。
- **成本**：低中。ExecutionState 已有全部信息，缺的是采集与导出。
- **依赖**：无。随时可做。
- **建议**：与 A 同期做——接真 LLM 后排查识别问题全靠它。

### 方向 F：应用化（产品形态）

**内容**：包装成可用工具——独立 CLI agent（REPL 对话式文件助手）、
或集成进 pi coding agent 作为扩展。

- **价值**：取决于目标。若目标是验证架构的实用价值，这是终极检验。
- **成本**：高（超出原型范畴）。
- **依赖**：A（真 LLM）+ B（会话）+ E（可调试性）基本就绪后才有意义。
- **结论**：远期目标，不是下一步。

### T1 经验库搜索 + L4 任务编排（2026-08-20 定位升级）

> 定位修正：T1 不只是「检索工具」，而是 **L4 规划回路的核心组件**。
> L4 的职责由此从「intent 分类器」升级为「任务规划器（planner）」。

#### 1.1 L4 规划回路的完整形态

```
用户话语（任务目标，可能需要多个步骤才能完成）
   ↓
L4 规划器：
  ① 理解任务目标 → 分解为子目标（0 个或多个）
  ② 对每个子目标：search(子目标描述) → 候选经验元数据 top-k
  ③ 基于元数据评估每个候选：
       - 能力匹配：inputs 能否满足（来自用户/上游经验输出/literal）
       - 数据衔接：本经验的 outputs 能否作为下游经验的输入
       - 副作用可接受？（T4 副作用声明）
  ④ 生成编排计划：一个或多个经验调用 + 参数数据流
   ↓
编排计划 → 逐个 L3 编译 → L1 执行
```

**搜索在回路中的位置**：它是 L4 的「能力感知」来源——
L4 接收两方面输入：①人类自然语言的任务目标；②经验库可用经验的
元数据（经搜索召回的相关子集）。没有 ②，L4 只能瞎猜系统能做什么；
有了 ②，L4 的规划是**有依据的能力匹配**。

#### 1.2 编排计划的表示——关键架构决策

L4 动态编排的产物是什么？三个选项：

- **选项 a（推荐）：合成经验（Synthesized Experience）**
  L4 生成一个临时 Experience：target steps 引用多个已有经验
  （嵌套调用模式——`setup_workspace` 就是它的手写版）。
  **复用现有 L3 编译器，零引擎改动**；且「高频编排固化入库」
  就是把这个临时经验转正——经验演化闭环自然形成。
- 选项 b：新计划类型 IntentPlan，pipeline 逐个执行——引入平行机制，碎片化
- 选项 c：L4 输出多轮 intent 顺序 say——无数据流衔接，能力最弱

#### 1.3 元数据的「能力接口」需求升级

L4 要做编排判断，元数据必须构成**能力接口契约**（不只是描述文字）：

| 元数据 | 编排判断中的用途 |
|---|---|
| inputs ParamSpec | 这个经验需要什么——上游输出/用户输入能否满足 |
| outputs ParamSpec | 这个经验产出什么——能否衔接下游 |
| 副作用声明（T4） | 编排顺序约束（只读可重排/写操作需保序）|
| description 语义质量 | 检索召回率的基础（三重读者：L4 prompt/检索字段/人类文档）|

#### 1.4 搜索接口草案

```ts
interface ExperienceSearch {
  // query: L4 生成的子目标描述（或其 embedding）
  search(query: string, k?: number): ExperienceMetadata[]
}
interface ExperienceMetadata {
  id: string
  description: string
  tags: string[]
  inputs: Record<string, ParamSpec>
  outputs: Record<string, ParamSpec>
  sideEffects: SideEffect[]   // T4
  version: string
}
```

#### 1.5 设计时场景（不变）

作者/LLM 入库前查重——「是否已有类似经验」。实现梯度：
1. 结构化检索：id/description/tags 关键词匹配（零依赖，先行）
2. 语义检索：description 向量化（接真 LLM 后顺带获得 embedding）
3. 混合排序：结构过滤 + 语义相似度

#### 1.6 动态编排 vs 经验固化（与方向 C 的闭环）

- **动态编排**处理长尾任务（每次现场规划）
- **固化**把高频编排沉淀为正式经验（转正后可被后续编排复用，形成层级）
- 两者互补：固化降低平均规划成本，动态保证长尾覆盖
- 这正是「经验演化闭环」的引擎：使用日志 → 高频编排模式 → 固化 → 库增长

### T2 设计时可视化

**两个可视化对象**：
- **经验静态视图**：三段式 JSON → Mermaid flowchart
  （pre 链 → judgment 菱形 → then/else 路径 → target steps），
  让「读一条经验」从读 JSON 变成看流程图。
- **编译产物视图**：compileExperience 输出的 StackEntry 序列渲染为

**价值**：经验作者的创作反馈回路；评审工具；文档自动生成。
**成本**：低。Mermaid 是纯文本可直接嵌入 markdown/GitHub 渲染，无需 Web UI 起步。
**依赖**：无。现在就可做（9 条经验已经不好直接读 JSON 了）。

### T3 LLM 辅助经验设计

**内容**：从自然语言场景描述 / 使用日志生成经验草稿，人审后入库。

**关键洞察——校验器已经存在**：
LLM 生成的草稿要过三关才能入库，而这三关 MVP 已全部具备：
1. Schema 校验：TypeScript 类型 + ParamSpec
2. 引用校验：compileExperience 天然拒绝未知 op / 不存在的 path / 缺失 required 输入
3. 行为验证：编译产物在沙箱 state 试跑（demos 的 run 模式即模板）

即：**编译器就是经验草稿的最佳验收器**。LLM 只负责生成，正确性由既有设施把关。

**与方向 A 的区分**：A 是运行时 LLM（识别 intent），T3 是设计时 LLM
（生成经验）——两次调用、两种 prompt、不同质量要求（T3 产物需人审）。

**依赖**：A（真 LLM 接入可复用）；T4（生成的经验需带完整元数据）；T1（入库前查重）。

### T4 经验元数据规范 → 编译器消费

**现状**：经验已有的隐式元数据 = inputs/outputs ParamSpec（编译器仅用
required/default）+ handleError + responses。

**候选元数据及消费方**：

| 元数据 | 消费方 | 用途 |
|---|---|---|
| tags / category | T1 搜索 / T3 查重 | 检索字段 |
| ParamSpec.type 强制校验 | 编译器 | 编译期校验 ParamRef 字面量与声明类型一致（当前不查）|
| 副作用声明（read-only / fs-write / exec）| 编译器 → 安全策略 | 高危经验标记需确认；只读经验可并行/缓存 |
| 版本号 + 兼容范围 | 演化流程 | 经验修订时不破坏旧调用方 |
| 超时/重试策略 | 编译器 → entry 属性 | 替代硬编码默认值 |

**定位**：T4 是 T1/T3 的地基——先定 schema，其余模块消费它。
其中「ParamSpec.type 编译期校验」和「副作用声明」两项即使独立于工具链
也直接提升引擎健壮性。

### 工具链内部依赖关系

```
T4 元数据规范（地基——能力接口契约）
 ├─→ T1 搜索+编排（消费 tags/schema/副作用；L4 规划回路的核心组件）
 └─→ T3 LLM 辅助设计（生成需带元数据；入库前 T1 查重）
T2 可视化（独立，随时可做；合成经验同样需要可视化）
```

A 的第一期可以只做单经验识别（现状模型），A 的第二期（编排）以 T1 为核心。
