## 决策摘要

LLM 辅助设计模块的能力定义：**把「编写一条新经验」的成本从
人工构造 JSON 降为「描述场景 + 审核确认」**——LLM 根据场景描述
生成经验草稿，经既有校验设施把关、人类审核后入库。

关键立场：**LLM 只负责生成，正确性由既有设施把关**——
MVP 的编译器与类型系统天然构成经验草稿的验收器，无需发明新的验证机制。

---

## 一、解决什么问题

1. **编写成本**：一条合格经验需要正确表达前置/条件/路径/步骤/
   寄存器传递/回复消息——手工构造慢且易错。
2. **规模化瓶颈**：经验库从 9 条到 50+ 条靠手写不现实（方向 C 的前提）。
3. **知识沉淀断层**：真实使用中出现的重复编排模式，缺乏低成本
   转化为经验的通道。

## 二、能力边界

**做**：
- 从自然语言场景描述生成经验草稿（完整三段式定义）
- 为草稿自动附加元数据（标签、副作用声明初稿）
- 生成后自动过校验，输出校验报告供人审

**不做**：
- 不自动入库（人审是必经环节）
- 不修改既有经验（修订流程另行讨论）
- 不保证草稿业务语义正确（LLM 可能写出「能跑但不对」的经验——
  人审重点正是语义而非语法）

## 三、预期输入 / 输出

| | 表达 |
|---|---|
| **输入** | 场景描述（自然语言：这个经验要做什么、输入是什么、正常/异常时各期望什么）|
| **辅助输入** | 元数据规范（doc 17）、相似经验示例（doc 14 搜索召回）、可用 L2 op 清单 |
| **输出** | 经验草稿（**XML 中间定义**，见 doc 15——非 L3 JSON）+ 校验报告 + PlantUML 可视化预览 |

> **D-E2-1 联动修正（2026-08-20）**：LLM 直接编辑的对象是 XML 中间定义
> （业务语义 + 图形结构，无寄存器等运行时细节），L3 JSON 由
> 「XML→L3 编译模块」基于拓扑不变性推导生成。理由：
> ① 人类/LLM 不应接触执行细节；② XML 表达自由度允许选择最适合
> 理解的粒度（复杂表达式可单节点或拆分分支），编译保证语义等价；
> ③ 防止 LLM 向 L3 结构同构侵蚀设计抽象。

## 四、预期行为表达（示例）

> 以下为**预期效果**的描述性示例，非实现规格。

- 输入场景「读取 CSV 文件并统计行数」→ 预期产出草稿：
  pre 用 file_read 读内容；target 用 evaluate_expr 组合求行数；
  带失败消息模板与副作用声明（只读）。**同时预期明确说明**：
  若现有 `read_file` 已覆盖读取部分，草稿应复用而非重造。
- 输入的场景若与库中已有经验语义重复 → 预期先触发查重提示
  （引用 doc 14 搜索），由人决定放弃/合并/仍新建。
- 生成的草稿引用了不存在的 op 或 path → 预期被编译器校验直接拒绝，
  校验报告指出具体问题，LLM 可据此修正（自动迭代或人工介入）。
- 草稿通过全部校验后 → 预期附可视化预览（doc 15）供人审，
  人审通过才入库。
