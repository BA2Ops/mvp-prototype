## 决策摘要

本模块的能力定义：**推理补全器**，而非格式转换器。

> **XML 中仅收集用户可提供的信息。** 编译器基于用户提供的信息，
> 以及系统自身能力、设计哲学和逻辑、系统 L3/L2/L1 的实际实现和能力，
> **推理补全所有其他信息**，生成完整可执行的 L3 Experience 定义。

用户与编译器的分工：

| | 用户（经 XML）| 编译器（推理补全）|
|---|---|---|
| 表达什么 | 业务意图：做什么、顺序、数据从哪来到哪去、分支含义 | 一切执行机制 |
| 需要知道 | 节点引用的经验/op + 参数 + 关系 | 系统全部实现细节 |

### 补全主轴（2026-08-20 进一步聚焦）

> **需要推理补全的主要是：寄存器和业务变量/常量之间的映射。**
>
> XML 的世界里只有**业务变量**（节点参数名：path、content、find…）
> 和**常量值**；L3 的世界里只有**寄存器**（$r_input_path、$r_content、
> $r_argtmp_N…）。两者之间的整张映射表就是编译器的核心产物：
>
> | 业务世界（XML）| 映射（编译器核心工作）| 寄存器世界（L3）|
> |---|---|---|
> | 经验输入参数 path | Step 0 输入绑定 | $r_input_path |
> | 常量 'foo' | sidecar move | $r_argtmp_N |
> | 节点输出 content | op 执行后 move 物理输出槽 → 业务变量 | $r_content |
> | 连接 B.text ← A.content | A 输出 move 到 $r_content,B 输入从 $r_content move 到 B 的物理输入槽 | $r_content（业务变量区中转）|
>
> 其余补全（分支骨架计算、汇聚落点、回环结构）都是这张映射表
> 在控制流场景下的延伸应用。

## 核心裁定（2026-08-20）：图形节点 = 现有 L3 经验的明确引用

**用户必须基于现有 L3 经验列表，明确选择已存在的特定经验关联到图形节点。**
因此编译器**无需推断**即可知道每个节点的：

- **输入契约**：来自被引用经验的 `inputs` schema
- **输出契约**：来自被引用经验的 `outputs` schema
- **错误契约**：来自被引用经验的 `responses.failure`

> 例：用户从经验列表选择「读取文件」→ 节点即 `read_file` 经验的实例化。
> 编译器直接读其定义：输入 `path`、输出 `content`、失败消息
> 「读取失败：文件 {path} 不存在」——**全部是既有事实，零语义推断**。

### 推理补全范围的收窄与纯化

原「节点类型目录 → op 模板推断」模型废弃。补全范围收窄为
**纯结构机械推导**（确定性程序，无语义判断）：

| 保留的推导（结构机械）| 废除的推导（语义推断）|
|---|---|
| 参数连接 → 寄存器分配与绑定 | ❌ 业务节点类型 → op 的映射 |
| 顺序界定 → pre/steps 结构归属 | ❌ 错误处理意图 → 策略选择 |
| 分支骨架 → cskip/skip 计算 | ❌ 条件语义 → 表达式的「理解」|
| 汇聚/回环 → 结构变换 | |

契约全部来自被引用经验的既有定义——**推理退化为查表 + 结构变换**。

### 节点类型与 L1 映射（2026-08-20 裁定）

三类节点，各自有明确的 L1/L2/L3 映射目标：

| 节点类型 | 用户用法 | 契约来源 | 映射目标 |
|---|---|---|---|
| **经验节点**（子节点/子经验）| 引用现有 L3 经验 | 该经验的 inputs/outputs/responses | execute_intent 嵌套帧 |
| **op 节点** | 引用 L2 op | formalSpec（错误契约按哲学补默认）| execute_op |
| **条件节点** | 业务问题分支 | 分支条件引用上游输出参数 | evaluate_expr 求值 + **conditional_skip（L1 条件跳转指令）** |

要点：

- **经验节点即子经验**：编排产生的合成经验中，引用现有经验的节点
  在运行时就是一次子经验调用（execute_intent 帧），与 setup_workspace
  模式完全一致。
- **条件节点直接对应 L1 条件跳转**：用户表达的业务问题
  （如「文件已存在？」）经求值后落到 L1 的 conditional_skip 语义上。
  编译器负责 D-C4-3 规范构造（求值 + cskip(n=len(THEN)+1) + 尾部 skip_n），
  用户不可见。
- **地基问题**：第一条经验从哪来？→ op 节点组装（doc 16 流程）或
  手写 L3（MVP 的 9 条即此方式）。经验节点编排不产生新经验；
  新能力经 doc 16 创建后即成为可引用的经验节点——层级自然生长。

## 一、推理补全的知识来源（编译器的「系统知识库」）

编译器不是猜测——所有补全都基于以下机器可读的系统知识：

| 知识来源 | 内容 | 补全示例 |
|---|---|---|
| **被引用经验的 L3 定义**（主要）| inputs/outputs schema、responses.failure | 节点参数端口、错误消息——直接读取，零推断 |
| **L2 formalSpec**（仅原子节点）| op 输入输出契约 | 原子节点的端口定义 |
| **L3 编译既有规则** | 输入绑定、分支构造、sidecar 装载、路径标记 | 参数连接 → 寄存器分配与 move（用户不可见）|
| **L1 约束** | execute_op 只读写 internal、literal 需 sidecar | 常量参数 → 自动 sidecar move |

（原「节点类型目录」概念随核心裁定废弃——节点即经验引用，无需中间映射层。）

## 二、推理补全的类别（用户信息 vs 补全信息对照）

| 用户在 XML 中提供 | 编译器推理补全（纯结构机械）|
|---|---|
| 节点 = 对现有经验的引用 + 参数来源 | 经验内 steps 的实例化与 sidecar 装载 |
| 顺序界定 | pre_processing 归属 / target steps 依赖序 |
| 参数连接（A.x → B.y）| 寄存器分配、inputs/outputs 地址绑定 |
| 字面量参数值 | sidecar move 装载 |
| 分支条件 = 上游输出参数（如 exists）| 条件表达式构造 + 分支骨架（cskip/skip 计算）|
| 汇聚参数意图 | 各分支落点与收尾绑定 |
| 受控回环 | 递归自嵌套结构 + 终止 judgment |

（结果消息/错误契约不再需要补全——直接继承被引用经验的
responses 定义。仅原子节点按设计哲学补默认。）

**原则**：用户提供的越少，编译器补全的越多——但补全永远基于上表
知识来源，**确定性、可解释、可复现**（同输入同输出，无随机性）。

## 三、预期行为表达（示例）

> 描述性示例，非实现规格。

- 用户只画了一个「读取文件」节点（路径参数来自输入）
  → 预期产出完整 L3：file_read 步骤、content/error 输出绑定、
  ENOENT 失败消息模板——**用户一个字都没提错误处理**，
  系统哲学自动补全。
- 用户画判断「文件已存在？」→ 预期编译为基于 file_read 错误语义的
  条件表达式（具体表达式形式用户不可见），并生成完整分支骨架。
- 用户提供的两条信息存在冲突（如顺序界定成环且无终止判断）
  → 预期**编译失败并指出需要用户澄清什么**，而非猜测。
- 同一份 XML 重复编译 → 预期产出语义一致（理想情况下逐字节一致）的 L3。

## 四、能力边界

**做**：
- 基于系统知识库推理补全全部执行机制
- 信息完备性校验：无法补全时明确报告缺口（请求用户提供什么）
- 语义等价保证：同一 XML 的多次编译行为一致

**不做**：
- 不做业务语义的猜测（用户没表达的业务意图不会凭空出现）
- 不做非确定性的「智能」补全（本模块是确定性程序；创造性生成
  是 doc 16 LLM 辅助设计的职责，两者边界清晰）

## 评估记录：三节点 vs 当前 L3 条件模型（2026-08-20）

### 结论速览

| 节点 | 合理性 | 可编译出可用 L3 JSON |
|---|---|---|
| 经验节点 | ✅ | ✅ 子经验嵌套（setup_workspace 已验证）|
| op 节点 | ✅ | ✅ |
| **条件节点** | ⚠️ 语义合理 | ⚠️ **仅「尾部分支」形态可编译** |

### 当前 L3 条件模型的三个结构性限制

L3 的 ConditionalJudgment 是**声明式**（condition_expr + then/else path
ID 引用），**不直接对应** L1 跳转——conditional_skip 由 L3→L1 编译
（D-C4-3 规范构造）生成。其结构性限制：

1. 条件是**经验级结构**，不在 steps 流中——不能出现在流程中间
2. **无「分支后汇合」表达**——then/else path 是两条终点路径，
   「分支 → 处理 → 汇合继续共同尾部」无法表达
3. 多条件仅支持 **else-if 链**——两个独立位置的 if 无法表达

反例：`[读文件] → [已存在?] →是→ [跳过] ─┐→ [读取验证]`
（分支后汇合）无法用当前 L3 正确定义。

## 最终裁定（2026-08-20）：XML 自由表达 + L3 单职责 + 规范化编译

### L3 的编程模型约定（保持不变）

L3 坚持**一个函数一个职责**的传统程序编码约定。每条经验虽可
进行子经验调用，其本身遵循经典的函数内部结构：

```
① 数据准备：用输入参数做数据转换，
   或调用子经验（子函数）获取额外数据
② 条件检验：逐项检验 → 不满足则提前结束（业务错误路径）
③ 主业务操作：通过全部检验后，执行真正该做的业务操作
```

即 **guard clause / 提前返回**模式——当前 L3 的
`conditional_judgment + paths` 模型正是此形态，**无需任何扩展**。

### 两层的分工

| 层 | 流程表达能力 | 服务对象 |
|---|---|---|
| **XML 中间定义** | 自由的结构化分支（中间分支、汇合、嵌套——上节全部能力保留）| 照顾人类用户的表达自由 |
| **L3 Experience** | 单职责函数 + guard clause（现状模型）| 执行的简洁性与一致性 |

### 规范化编译（XML→L3 的核心变换）

两层之间进行数据清理与转换，达成**语义不变、处理逻辑不变**
前提下的结构规范化：

```
XML（自由图）:
[读文件] → [文件已存在?] ─是→ [跳过] ─────────┐
                         └否→ [处理] → [写回] ┴→ [读取验证]

L3（规范化后，guard clause 形态）:
pre:  [读文件]
judgment: 文件已存在?
  paths.skip:    [跳过] → [验证]*       ← 共同尾部复制进各分支
  paths.process: [处理] → [写回] → [验证]*
```

语义不变（验证在任一路径恰好执行一次）、处理逻辑不变、
结构由自由图规范化为单职责形态。

**规范化编译的预期变换类别**（⚠️ 完整版为待处理项，见下）：
- 汇合点识别 → 共同尾部复制（hoisting 进各分支）
- 自由图 → guard clause 形态归整（检验链 + 主操作）
- 参数数据流 → 寄存器映射（§补全主轴）
- 受控回环 → 递归自嵌套结构

**代价（明确接受）**：规范化可能造成 L3 JSON 的步骤重复
（如上例 [验证] 出现两次）。换取的是 L3 模型永不复杂化——
执行层保持极简一致。

## 当前阶段策略（2026-08-20 裁定）：受限子集先行

> **裁定**：XML→L3 的完整规范化编译涉及较为困难的部分，
> **暂记为待处理项**。当前 MVP / 演示项目 / 实际使用中，
> 要求用户的 XML **不能进行过于自由的定义**——以简单验证规则
> 强行限定 XML 落在「易于理解、可较简单转化为 L3 预期结构」的
> **受限子集**内。

### 受限子集的验证规则（预期表达）

| # | 规则 | 校验方式 |
|---|---|---|
| R1 | 条件节点仅允许**尾部分支**：分支后不得有汇合节点 | 图遍历：判断节点的所有后继到终点路径不得交汇 |
| R2 | 树形结构：每节点至多一个前驱（起点除外），无任意汇合 | 前驱计数 |
| R3 | 多条件仅限 else-if 链（与 L3 judgment 链语义一一对应）| 判断节点后继结构检查 |
| R4 | 回环仅允许指向经验入口的受控回环（递归模式）| 回边目标检查 |
| R5 | 数据流单来源 + 类型兼容（§3.6.2 已有）| 参数端口检查 |

全部规则均为**简单图检查**（遍历+计数），无需任何结构变换——
因此第一阶段编译器 = 「子集校验 + 直接映射」，实现成本低。

### 两阶段路线

```
阶段一（现在）：受限子集校验 + 直接映射编译
   └─ 校验失败时给出引导：「请将图形调整为…形态」
阶段二（待处理项）：完整规范化编译
   └─ 开放自由图形态；汇合复制/guard 归整等变换落地后
      逐步放开 R1-R3 的限制（R4/R5 为长期约束）
```

### 待处理项登记

| 项 | 内容 | 解锁条件 |
|---|---|---|
| TP-1 | 完整规范化编译（汇合复制/guard 归整）| 真实需求中出现受限子集无法表达的业务流程 |
| TP-2 | while 型条件块（块内回环）| 同上 |
