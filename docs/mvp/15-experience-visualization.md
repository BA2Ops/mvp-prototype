## 决策摘要（2026-08-20 用户裁定）

1. **图形表达选定 PlantUML 语法**；本模块**不需要编辑能力**——
   只做「中间定义 → PlantUML 文件」的转换工具。
2. **引入 XML 中间定义层**：可视化与 LLM 辅助设计的核心信息载体和产物
   是 XML 中间定义，**不是 L3 JSON**。
3. XML 以**图形表达为核心**，只含语义/业务含义的信息；
   **不包含 L1 运行时细节**（寄存器、表达式 AST、跳转计数等）——
   人类用户不需要接触这些。
4. **XML 图形内容不要求 100% 匹配 L3 结构**——表达自由度是特性
   （见 §四）。
5. 未来应有「**XML → L3 JSON 编译模块**」：基于处理逻辑/拓扑不变性
   进行优化编译，生成最终 L3 定义。

由此确立**三层编译架构**：

```
人类作者 / LLM 辅助设计（doc 16）
      ↓ 编辑（唯一的设计入口）
XML 中间定义 ──── 设计视图：业务语义 + 图形结构
      ↓ 【新模块】XML→L3 编译（拓扑不变性优化）
L3 Experience JSON ──── 执行定义
      ↓ compileExperience
L1 指令序列 → L2 → 真实世界

PlantUML 文件 ←── 转换工具（本模块；人类阅读/评审/文档）
```

---

## 一、解决什么问题

1. **阅读成本**：经验 JSON（pre 数组 + 条件树 + paths/steps）人类难以直读，
   `safe_write` 这样的中等复杂度经验已需来回跳读。
2. **创作反馈缺失**：作者写完经验后没有直观方式确认「结构是否符合意图」。
3. **设计/执行耦合**：若 LLM 辅助设计直接改 L3 JSON，人类被迫接触
   寄存器、表达式 AST 等执行细节——**设计语义与执行语义应分层**。

## 二、能力边界

**做**：
- 定义 XML 中间格式的语义（节点/边/属性的业务含义）
- 工具：读取 XML 中间定义 → 生成 PlantUML 语法文件（只转换，不编辑）
- （关联新模块，见 §六）XML → L3 JSON 的编译

**不做**：
- 图形编辑能力（编辑由人类改 XML / LLM 辅助设计改 XML）
- 寄存器分配、表达式构造等执行细节的任何表达
- 交互式 Web 界面（静态文件生成即可）

## 三、XML 中间定义的能力边界

### 3.1 包含（语义/业务含义）

| 信息 | 预期表达 |
|---|---|
| 流程结构 | 前置步骤、判断分支、动作、路径——以业务语言命名 |
| 条件语义 | 「文件已存在？」「计数达到目标？」——**业务问题**，非求值表达式 |
| 节点业务属性 | 名称、语义描述、结果消息、副作用标记 |
| 子流程引用 | 嵌套调用其他经验（按经验 ID/名称）|
| 人类批注 | 原生注释（XML 原生支持，设计文档刚需）|

### 3.2 不包含（L1/L3 运行时细节）

寄存器名（$r_*）、evaluate_expr AST、conditional_skip/skip_n 跳转计数、
错误码判断逻辑、输入绑定 move——这些由 XML→L3 编译模块推导生成。

### 3.3 表达自由度（特性，非缺陷）

**XML 图形不必 100% 匹配 L3 结构**：

- 表达 A：单个判断节点「计数达到目标？」——复杂关系压缩为一个节点
- 表达 B：连续分支「+1 → ≥目标？→ 是/否」——拆分为更简单的可视化结果
- 两者**编译为同一 L3 语义**——处理逻辑/拓扑不变性由编译模块保证

这如同高级语言与 IR 的关系：同一语义允许多种设计表达，
编译器负责等价转换。人类/LLM 选择**最适合理解和交流**的粒度，
执行粒度交给编译。

## 四、XML vs JSON 的选型评估（已裁定：XML）

| 维度 | XML | JSON | 意义 |
|---|---|---|---|
| **与 L3 的关系** | 刻意不同构 | 同构诱惑强 | **决定性**：中间层价值在于「设计语义 ≠ 执行语义」的分离；JSON 的同构性会诱导向 L3 靠拢，侵蚀抽象 |
| 注释 | 原生支持 | 无 | 设计批注刚需 |
| 属性/子结构区分 | 属性 vs 子元素 vs 文本 | 键值扁平 | 图形节点 = 元数据(属性) + 子结构(元素)，表达自然 |
| 程序读写（TS） | fast-xml-parser 等成熟 | 原生 | JSON 略优，非决定性 |
| LLM 生成/编辑 | 语料充足；XPath 定位修改成熟 | structured output 好 | JSON 略优，非决定性 |
| 校验 | 解析后 Zod 验证（绕开 XSD 工具链）| Zod 直接 | 等价 |

**架构验证结论**：程序读写、动态编辑、LLM 兼容三项 JSON 略优但均可满足；
「防同构侵蚀」与「注释」两项 XML 具备而 JSON 缺失——**XML 胜出**。

## 五、PlantUML 转换的预期行为表达

> 描述性示例，非实现规格。

- 输入 `safe_write` 的 XML → 预期输出 PlantUML activity 图：
  探测读取 → 条件「文件已存在？」→ 是：跳过（附回复消息）/ 否：写入。
  图中**不出现**任何寄存器名或错误码。
- 输入含子流程引用的 XML → 预期输出引用节点（如「→ replace_in_file」），
  不内联展开（展开层级是查看者的需求，属渲染选项）。
- 批量模式：对整个经验库生成索引页（每经验一图 + 概要）。

## 六、衍生新模块：XML → L3 编译（拓扑不变性优化）

本决策催生一个新模块（独立讨论稿待建）：

- **能力定义**：读取 XML 中间定义，基于处理逻辑/拓扑不变性
  优化编译，生成 L3 Experience JSON。
- **预期行为**：§3.3 的表达 A 与表达 B 编译出语义等价的 L3；
  寄存器分配、条件表达式构造、错误码判断、回复消息挂载均由编译推导。
- **验证方式**：同一 XML 编译产物可执行且行为一致；
  既有经验（手写 L3）可反向对照验证编译语义。
