## 决策摘要（2026-08-20 用户裁定）

1. **图形表达选定 PlantUML 语法**；本模块**不需要编辑能力**——
   只做「中间定义 → PlantUML 文件」的转换工具。
2. **引入 XML 中间定义层**：可视化与 LLM 辅助设计的核心信息载体和产物
   是 XML 中间定义，**不是 L3 JSON**。
3. XML 以**图形表达为核心**，只含语义/业务含义的信息；
   **不包含 L1 运行时细节**（寄存器、表达式 AST、跳转计数等）——
   人类用户不需要接触这些。
4. **XML 图形内容不要求 100% 匹配 L3 结构**——表达自由度是特性
   （见 §四）。
5. 未来应有「**XML → L3 JSON 编译模块**」：基于处理逻辑/拓扑不变性
   进行优化编译，生成最终 L3 定义。

由此确立**三层编译架构**：

```
人类作者 / LLM 辅助设计（doc 16）
      ↓ 编辑（唯一的设计入口）
XML 中间定义 ──── 设计视图：业务语义 + 图形结构
      ↓ 【新模块】XML→L3 编译（拓扑不变性优化）
L3 Experience JSON ──── 执行定义
      ↓ compileExperience
L1 指令序列 → L2 → 真实世界

PlantUML 文件 ←── 转换工具（本模块；人类阅读/评审/文档）
```

---

## 一、解决什么问题

1. **阅读成本**：经验 JSON（pre 数组 + 条件树 + paths/steps）人类难以直读，
   `safe_write` 这样的中等复杂度经验已需来回跳读。
2. **创作反馈缺失**：作者写完经验后没有直观方式确认「结构是否符合意图」。
3. **设计/执行耦合**：若 LLM 辅助设计直接改 L3 JSON，人类被迫接触
   寄存器、表达式 AST 等执行细节——**设计语义与执行语义应分层**。

## 二、能力边界

**做**：
- 定义 XML 中间格式的语义（节点/边/属性的业务含义）
- 工具：读取 XML 中间定义 → 生成 PlantUML 语法文件（只转换，不编辑）
- （关联新模块，见 §六）XML → L3 JSON 的编译

**不做**：
- 图形编辑能力（编辑由人类改 XML / LLM 辅助设计改 XML）
- 寄存器分配、表达式构造等执行细节的任何表达
- 交互式 Web 界面（静态文件生成即可）

## 三、XML 中间定义的能力边界

### 3.1 包含（语义/业务含义）

| 信息 | 预期表达 |
|---|---|
| 处理节点 | **按业务类型分类**（见 §3.4），以业务语言命名 |
| 条件语义 | 「文件已存在？」「计数达到目标？」——**业务问题**，非求值表达式 |
| 节点业务属性 | 名称、语义描述、节点参数/内容、结果消息、副作用标记 |
| 顺序界定 | 用户显式定义「A 必须在 B 之前」的执行约束 |
| 数据/参数传递 | 用户显式定义「B 的某参数来自 A 的结果」的数据流关系 |
| 子流程引用 | 嵌套调用其他经验（按经验 ID/名称）|
| 人类批注 | 原生注释（XML 原生支持，设计文档刚需）|

> ⚠️ **两条边界原则**：
> 1. XML 中不存在「前置节点」概念——那是 L3 的执行阶段划分
>    （pre_processing），属于运行时细节。用户视角只有「处理节点 +
>    顺序界定 + 数据/参数传递」。业务流程图到 L3 三段式的映射由
>    编译模块推导（见 §3.5）。
> 2. **XML 仅收集用户可提供的信息**——其余一切由 XML→L3 编译器
>    推理补全（见 [doc 18](./18-xml-to-l3-compiler.md)）。

### 3.2 不包含（L1/L3 运行时细节）

寄存器名（$r_*）、evaluate_expr AST、conditional_skip/skip_n 跳转计数、
错误码判断逻辑、输入绑定 move——这些由 XML→L3 编译模块推导生成。
节点输出 `as` 字段保留寄存器名(op 输出→寄存器映射,供 move 指令使用);
输出绑定 `outputBindings` 用 `fromNode`(节点输出引用)代替直接引用寄存器名。

### 3.3 表达自由度（特性，非缺陷；⚠️ 当前受限于受限子集）

> **当前阶段（2026-08-20 裁定）**：完整的表达自由依赖 XML→L3 的
> 复杂规范化编译（待处理项，见 [doc 18](./18-xml-to-l3-compiler.md)）。
> 在此之前，XML 被**简单验证规则限定在受限子集内**：
> 条件节点仅尾部分支 / 树形无汇合 / else-if 链 / 入口受控回环 /
> 数据流单来源。校验失败时引导用户调整图形形态。
> 本节描述的完整表达自由是目标态，随规范化编译落地逐步开放。

**XML 图形不必 100% 匹配 L3 结构**：

- 表达 A：单个判断节点「计数达到目标？」——复杂关系压缩为一个节点
- 表达 B：连续分支「+1 → ≥目标？→ 是/否」——拆分为更简单的可视化结果
- 两者**编译为同一 L3 语义**——处理逻辑/拓扑不变性由编译模块保证

这如同高级语言与 IR 的关系：同一语义允许多种设计表达，
编译器负责等价转换。人类/LLM 选择**最适合理解和交流**的粒度，
执行粒度交给编译。

### 3.4 节点类型设计原则——符合业务逻辑表达预期

节点类型按**业务语义**分类，而非 L3 执行阶段。候选类型方向
（最小完备集待定）：

| 类型方向 | 业务含义示例 |
|---|---|
| 数据获取 | 读取文件、执行命令、查找文件 |
| 判断 | 业务问题（产生分支），如「文件已存在？」「达到目标？」|
| 处理/转换 | 内容替换、排序、截取、计算 |
| 输出/写入 | 写文件、保存结果 |
| 子流程 | 调用另一条经验 |

每个节点携带**类型对应的参数/内容**（如「读取文件」节点带路径参数、
「替换」节点带查找/替换内容）——**这正是用户关心的核心信息**：
每个节点的类型和对应参数，其余一切由编译推导。

### 3.5 用户定义的关系 → L3 三段式的编译映射

用户只定义两种关系，L3 结构由编译模块推导：

| 用户定义 | 编译推导（XML→L3 模块职责）|
|---|---|
| 顺序界定（A 先于 B）| 无上游依赖的获取类节点 → pre_processing 候选；其余按依赖序进入 target 路径 steps |
| 数据/参数传递（B.p ← A.result）| 寄存器分配与 execute_op inputs/outputs 绑定 |
| 判断节点 | conditional_judgment + then/else paths（条件表达式由条件语义推导）|
| 路径回复消息 | TargetOpPath.response |

### 3.6 参数级数据流语义

数据传递的连接单位是**参数**而非节点：「后续节点的某个输入参数」
对应「另一节点的某个输出参数」。例：

```
[读取文件] ──content──→ [替换内容].text
                          [替换内容].find  ← 字面量 "foo"
```

#### 3.6.1 节点的参数契约

每个节点类型隐含两组**端口**：

| 端口 | 来源 | 示例（「替换内容」节点）|
|---|---|---|
| 输入端口 | 节点类型定义的必需/可选参数 | text（必需）、find（必需）、replace（必需）|
| 输出端口 | 节点执行后产生的结果 | result（替换后文本）、count（替换处数）|

端口即节点类型的「能力接口」——与 doc 17 的 ParamSpec 同源，
XML 校验时输入输出的类型应兼容（string 接 string，不接 number）。

#### 3.6.2 连接规则（预期语义）

| 规则 | 预期 |
|---|---|
| 单来源 | 一个输入参数至多连接一个输出端口（无多路复用歧义）|
| 字面量直供 | 输入参数可不连接，直接给常量值（find = "foo"）|
| 必填未连接 | 图不完整 → 校验失败并指出缺口（哪个节点的哪个参数悬空）|
| 可选未连接 | 允许，行为按该参数的缺省语义 |
| 类型兼容 | 连接两端类型应一致/可转换，否则校验警告或失败 |

#### 3.6.3 分支汇聚问题（判断节点的特殊地位）

判断节点产生两条分支，各分支可能产出不同结果，下游如何引用？
预期引入**汇聚输出**概念：判断节点（或其路径块）声明
「无论走哪条分支，此参数最终都有值」——

```
[文件已存在？] ─是→ [跳过写入].bytes=0 ─┐
                └否→ [写入文件].bytes ──┴──→ 汇聚参数 bytes
```

下游引用 `bytes` 时无需关心走了哪条分支。
（类比编译器 SSA 的 phi 函数——但业务层只表达「汇聚」意图，
插入动作由编译完成。）

#### 3.6.4 回环数据流（循环场景）

递归经验中存在跨轮次的状态（如计数器的当前值）。
预期表达：允许边指回上游节点形成**受控回环**，
配合终止判断节点构成循环——编译模块负责将其映射为
L3 的递归自嵌套结构（Phase D 已验证的模式）。

#### 3.6.5 可视化表达

参数级连接在 PlantUML 中的预期呈现：
节点框内列出参数端口，连接线标注流动的参数名——
用户观察确认的核心正是「我要的数据流是否被正确表达」。

#### 3.6.5b 本地业务变量（命名连线）

**场景**：上游结果需要①一对多分发、②语义重命名、③跨分支汇聚时，
需要「有名字的本地业务量」作中转。

**预期表达**：数据流连线可**命名**——命名后的连线成为可引用的
**本地业务变量**，任何后续节点的兼容输入端口均可从它取值：

```
[读取文件].content ──(命名为 fileBody)──→ 多个下游引用 fileBody
```

- 未命名的连线 = 纯点对点直连（简单场景零负担）
- 同名赋值出现在两条分支 → 系统识别为汇聚（§3.6.3）
- 回环中更新同名变量 → 允许（配合受控回环边，如计数器）
- 经验顶层输入参数本质上是「入口处已命名的本地变量」——同一机制

**编译映射（黑盒）**：本地变量名 → 业务变量区（internalStore 中以 `$r_<name>` 为 key）；
上游 op 执行后编译器生成 move 将物理输出槽内容卸载到业务变量区，
下游 op 执行前编译器生成 move 从业务变量区装载到物理输入槽。
op 的物理寄存器由 formalSpec.slotIndex 决定，对其他 op 不可见。
用户只见业务名，不见物理寄存器。
未使用的本地变量 → 校验警告。

#### 3.6.5c 输入端口的来源表达

输入参数取值来源共三类，统一为「名字空间 + 端口选择」模型：

**名字空间 = 入口参数 ∪ 本地变量（命名连线）**——
入口参数本质是「入口处已命名的本地变量」（同一机制，§3.6.5b）。

| 来源 | 画布操作 |
|---|---|
| 入口输入参数 | 从画布顶部「入口参数带」（函数签名的可视化源端口区）拉线 |
| 节点返回变量 | 从上游输出端口拉线（命名后入名字空间）|
| 字面量常量 | 点击输入端口直接填值 |

三种来源画布上视觉可区分；XML 中对应 from=input:x / from=node:X.out /
literal=v 三种表达（示意）。

**校验预期**：
- 引用名必须存在于名字空间，否则失败并指出未知引用
- 类型兼容（与 doc 17 ParamSpec 对齐）
- 必填输入端口三选一必须满足，否则图不完整

**编译映射（黑盒）**：input:x → $r_input_x；
node:X.out → X 输出寄存器；literal → sidecar 装载。

#### 3.6.5d 经验返回值与节点结果的映射（出口返回带）

与入口对称：画布底部设**返回值带**（outputs schema 的汇端口区），
节点输出端口可连线到返回值端口——定义「经验的返回值来自哪个节点结果」。

**规则预期**：
- 多来源到同一返回值端口 = 汇聚，来源必须位于**互斥分支**
  （非互斥多来源 → 校验警告：执行序覆盖）
- 业务错误提前结束路径**允许不提供返回值**——required 返回值的
  校验标准是「至少一条成功可达路径提供」
- 前置获取节点产出的返回值同样直接连线（与步骤节点无区别）
- 连线即重命名：内部输出名可与经验返回值名不同

**编译映射（黑盒）**：节点 outputs → 经验结果寄存器绑定；
互斥分支多来源 → 各分支收尾绑定同一寄存器；重命名 → 内外名字映射表。

#### 3.6.5e 条件节点（MVP 裁定：单变量判断）

> **裁定（2026-08-20）**：条件节点**必须先通过独立的 op 节点或
> 子经验节点获得一个局部变量**，条件节点关联该局部变量进行判断。
> **一个条件节点仅接受一个变量进行判断。**

**预期形态**：

```
[📦 检查文件存在] ──exists──→ ◆ exists 为真？
                               ├─ 是 → …
                               └─ 否 → …

[📦 计数+1] ──count──→ [⚙ 计算 count≥目标] ──shouldStop──→ ◆ 为真？
                                                            ├─ 是 → 结束
                                                            └─ 否 → 回环
```

**要点**：
- 复杂比较（如 count ≥ target）不由条件节点表达——先用
  evaluate_expr 类 op 节点算出**布尔局部变量**，条件节点只做
  单变量真值判断。语义推断由此从编译器中彻底移除：
  判断依据永远是显式的变量连线。
- 判断所依赖的数据一定来自可见连线——无隐式依赖，可视化即完整因果。

**编译映射（黑盒）**：
- 变量已是布尔 → conditional_skip 直接以该寄存器为条件源
  （连 evaluate_expr 都不需要）
- 非布尔变量 → 自动插入真值求值步骤
- 分支骨架 → D-C4-3 规范构造

**校验预期（新增 R6）**：
- 条件节点必须恰好关联一个局部变量（连线缺失/多余 → 校验失败）
- 该变量应可真值化（布尔优先；其他类型给警告提示先经转换节点）

#### 3.6.6 抽象边界——数据装载对用户完全黑盒

**用户不涉及参数如何映射到寄存器，也不提供哪些变量或常量需要 move。**

用户视角的因果只有两步：

```
用户动作：「连接 A.content → B.text」或「给 B.find 常量 'foo'」
   ↓  （中间一切黑盒：装载方式、传递机制、存储位置）
系统保证：B 执行时 text 拿到 A 的结果 / find 拿到 'foo'
```

以下内容**在用户的世界观中不存在**（编译模块的内部职责，此处仅作
实现记录）：

| 用户不可见 | 编译模块内部对应 |
|---|---|
| 参数到寄存器的映射 | 寄存器分配/命名/复用 |
| 变量/常量的装载方式 | move 指令（含字面量 sidecar 装载）|
| inputs/outputs 绑定 | execute_op 地址解析 |
| 无消费者输出的处理 | 死代码消除（可选优化）|
| 汇聚参数的落点 | 各分支写入同一寄存器 / 路径收尾 move |
| 回环的实现方式 | 递归自嵌套结构 + 终止 judgment |

**检验标准**：一份 XML 中间定义的读者，应该能完整理解业务意图
而完全不知道系统底层有寄存器的存在。若任何用户可见物（图形、
消息、文档）泄漏了上述概念，即为抽象边界被破坏。

## 四、XML vs JSON 的选型评估（已裁定：XML）

| 维度 | XML | JSON | 意义 |
|---|---|---|---|
| **与 L3 的关系** | 刻意不同构 | 同构诱惑强 | **决定性**：中间层价值在于「设计语义 ≠ 执行语义」的分离；JSON 的同构性会诱导向 L3 靠拢，侵蚀抽象 |
| 注释 | 原生支持 | 无 | 设计批注刚需 |
| 属性/子结构区分 | 属性 vs 子元素 vs 文本 | 键值扁平 | 图形节点 = 元数据(属性) + 子结构(元素)，表达自然 |
| 程序读写（TS） | fast-xml-parser 等成熟 | 原生 | JSON 略优，非决定性 |
| LLM 生成/编辑 | 语料充足；XPath 定位修改成熟 | structured output 好 | JSON 略优，非决定性 |
| 校验 | 解析后 Zod 验证（绕开 XSD 工具链）| Zod 直接 | 等价 |

**架构验证结论**：程序读写、动态编辑、LLM 兼容三项 JSON 略优但均可满足；
「防同构侵蚀」与「注释」两项 XML 具备而 JSON 缺失——**XML 胜出**。

## 四点五、交互模式——LLM 辅助设计器中的可视化编辑循环

面向人类用户的预期交互（与 [doc 16](./16-experience-llm-assisted-design.md) 共同实现）：

```
基于现有经验库内容（可复制相似经验为起点）
   ↓
用户自然语言输入（「加一步：替换完成后检查文件大小」）
   ↓
LLM 理解意图 → 修改 XML 中间定义（增删改节点/关系）
   ↓
PlantUML 渲染 → 用户观察图形变更结果
   ↓
确认意图表达正确？→ 是：继续/完成；否：继续对话修正
```

**用户在这个循环中关心/操作的**：
- 每个处理节点的**类型**与**对应参数/内容**
- 节点间的**顺序界定**与**数据/参数传递关系**

**用户永远不需要接触的**：
- 「前置节点」等执行阶段概念
- 寄存器、表达式、跳转计数等运行时细节

快速确认意图表达正确性的关键 = 图形变更的**即时性**与**最小差异**
（每次只呈现本次修改影响的局部，而非整图重述）。

## 五、PlantUML 转换的预期行为表达

> 描述性示例，非实现规格。

- 输入 `safe_write` 的 XML → 预期输出 PlantUML activity 图：
  探测读取 → 条件「文件已存在？」→ 是：跳过（附回复消息）/ 否：写入。
  图中**不出现**任何寄存器名或错误码。
- 输入含子流程引用的 XML → 预期输出引用节点（如「→ replace_in_file」），
  不内联展开（展开层级是查看者的需求，属渲染选项）。
- 批量模式：对整个经验库生成索引页（每经验一图 + 概要）。

## 六、衍生新模块：XML → L3 编译（推理补全）

本决策催生的新模块已建立独立能力定义文档：
**[doc 18 XML→L3 编译器](./18-xml-to-l3-compiler.md)**。

核心定位（用户裁定）：**XML 中仅收集用户可提供的信息；编译器基于
用户提供的信息 + 系统能力/设计哲学/L3-L2-L1 实际实现，推理补全
所有其他信息**。是推理补全器，而非格式转换器。
