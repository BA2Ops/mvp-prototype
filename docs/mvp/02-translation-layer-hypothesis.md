# 02 - 翻译层假说

> 为什么"一切都是 X"的统一哲学几乎必然遇到边界？

---

## 核心论断

> **"一切都是 X" 的抽象成立，当且仅当存在一个确定性的"语义→X"编译/翻译过程。当这个过程是模糊的、概率性的，或者缺失的，抽象就会破裂。**

我们称之为 **翻译层假说**（Translation Layer Hypothesis）。

---

## 三种系统的对照

### CPU ISA：翻译层 = 微码 + 编译器（强确定性）

```
用户意图: "把两个数相加"
     ↓
[ C编译器 ]    ← 确定性：相同输入永远产生相同输出
     ↓
汇编: ADD RAX, RBX
     ↓
[ CPU微码 ]    ← 确定性：硬连线逻辑
     ↓
µops: uADD, uMOV
     ↓
[ 硬件执行 ]   ← 确定性：晶体管开关
     ↓
晶体管翻转
     ↓
✓ "一切都是指令" 完全成立
```

### Linux：翻译层 = 内核（强确定性）

```
用户意图: "读取文件内容"
     ↓
[ libc库 ]    ← 确定性
     ↓
syscall: read(fd, buf, len)
     ↓
[ 内核 VFS ]  ← 确定性：明确定义的文件抽象
     ↓
具体文件系统调用 (ext4, ntfs, ...)
     ↓
磁盘 I/O

⚠ "一切都是文件" 近似成立，但 ioctl / signal / mmap 暴露了翻译层无法覆盖的部分
```

### Pi（LLM agent）：翻译层 = LLM（概率性）

```
用户意图: "总结这个 repo"
     ↓
[ LLM ]       ← ⚠ 概率性：相同 prompt 可能产生不同工具调用
     ↓
工具调用序列: [read README, read package.json, ...]
     ↓
[ pi runtime ]   ← 确定性
     ↓
文件 I/O / shell 执行

✗ "一切都是工具调用" 不能完全成立
```

---

## 翻译层假说的形式化（直观版）

设：
- `I` = 用户意图空间
- `O` = 操作指令集
- `f: I → O` = 翻译函数

存在**完全**函数 `f`，当且仅当：

1. `I` 是有限的、封闭的（实际是开放的）
2. 每个意图在 `I` 中是**无歧义**的（实际经常歧义）
3. 每个意图**预先声明所有参数**（实际经常欠定）
4. 没有意图需要**复合操作**（实际经常需要）

**这四条假设全部不成立** → 完整翻译不可能。

---

## 三种翻译层的能力对比

| 维度 | 传统编译器 | 内核 | LLM |
|---|---|---|---|
| 正确性 | 可形式化证明 | 可形式化验证 | 只能经验评估 |
| 可重现性 | 100% | 100% | 温度>0 时不保证 |
| 错误处理 | 编译错误明确报错 | errno 明确 | 可能幻觉出不存在的结果 |
| 终止性 | 已知（停机问题限制下） | 已知 | 可能无限循环 |
| 可调试性 | 完整中间表示（IR） | 内核日志 | 黑盒 |
| 完备性 | 理论上可证明 | 可证明 | 永远无法证明"什么情况下一定失败" |

**LLM 是世界上功能最强大但可靠性最差的"编译器"。**

---

## "一切都是 X" 的纯度 vs 翻译层质量

| 系统 | 翻译层 | 翻译层成本 | "一切都是 X" 的纯度 |
|---|---|---|---|
| CPU | 微码 + 编译器 | 几十亿美元研发，40 年演化 | 极高 |
| Linux | 内核 | 数十亿美元研发，30 年演化 | 高 |
| 高阶语言 | 编译器/解释器 | 数百万到数十亿美元 | 高 |
| Pi | LLM | 数十亿美元 + 永久不可靠 | 中（且永远无法完全纯化） |

**结论**：翻译层越强大、越可靠，"一切都是 X" 的纯度越高。

---

## Pi 为什么必须显式管理翻译失败

```
LLM 翻译失败的表现        →   pi 的应对机制
─────────────────────────────────────────────
上下文窗口耗尽            →   /compact（手动压缩）
LLM 推理出错，需要回退    →   /tree（手动分支）
LLM 行为不符合预期       →   /settings（手动调整参数）
用户想注入领域知识        →   AGENTS.md（绕过 LLM 翻译）
用户想提供专业工具        →   extensions/skills（扩展翻译层）
LLM 不该执行某些操作      →   沙箱/容器（在翻译层外兜底）
```

**Pi 的设计哲学** = 接受翻译层不可靠 + 在每个失败模式上提供手动控制。

---

## 启发：AGI 是什么？

从翻译层假说看，**AGI 本质上就是一个"完美的语义编译器"**：

```
完美 AGI:
任意自然语言意图 → 100% 正确、100% 可重现的执行序列
```

AGI 这么难，不是因为"更聪明的 LLM"，而是因为：
1. **正确性证明**：当前 LLM 无法证明自己正确
2. **完备性**：当前 LLM 无法保证覆盖所有情况
3. **可调试性**：当前 LLM 是黑盒
4. **终止性**：当前 LLM 可能无限循环

---

## 对 MVP 设计的指导

MVP 的每一层都应该考虑：

1. **这一层的翻译质量如何？** （确定性 vs 概率性）
2. **这一层失败的影响范围？** （局部 vs 全局）
3. **能否在前一层拦截？** （越早拦截越好）
4. **失败是否可恢复？** （自动恢复 vs 人工介入）

**原则**：**尽可能把翻译推到确定性最强的层**（如规则表），把概率性的层（LLM）放在最上层（意图识别）。
