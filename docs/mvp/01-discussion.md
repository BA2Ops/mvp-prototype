# 01 - 完整讨论记录

本文档按对话顺序记录从最初问题到 MVP 结论的完整推导过程。

---

## 起点：pi 的 4 个基础能力

**事实**：pi 默认给 LLM 4 个工具：`read`, `write`, `edit`, `bash`（外加 3 个只读 `grep`, `find`, `ls`）。

**问题**：为什么 pi 没有采用 Linux "一切皆是文件"的哲学，而是包含了 `bash` 这个执行操作？

### 分析路径

1. **Linux 的"一切皆是文件"本质**：抽象的是字节流 + 文件描述符
2. **进程执行与文件 I/O 的语义差异**：
   - 文件：确定性、无副作用、无 exit code
   - 进程：非确定性、有副作用、有 exit code、有信号、有生命周期
3. **Linux 自己也不严格**：ioctl、mmap、signal 等都是"非文件"
4. **pi 的真实抽象**："一切皆是工具调用" + bash 作为元工具

**关键洞察**：bash 工具内部已经是"一切皆是 BashOperations"的抽象（可插拔 local/SSH/Container），这才是 pi 自己的"一切皆是 X"。

---

## 用户的类比：CPU 是"一切都是指令"

**用户的精妙观察**：进入 CPU 核心边界，处理单元只能看到：
- 指令流（有限、格式确定）
- 寄存器文件
- ALU 标志位

所有复杂性（缓存、流水线、分支预测、微指令）都被 ISA 抽象隐藏。

### 三种"一切都是 X"对比

| 哲学 | 统一抽象 | 视角主体 | 翻译层 |
|---|---|---|---|
| Unix | 一切都是文件 | 用户程序 | 内核（确定性） |
| CPU ISA | 一切都是指令 | CPU 硬件 | 微码（确定性） |
| LLM Agent | 一切都是工具调用 | LLM | **LLM 自身（概率性）** |

### 关键洞察

**"一切都是 X" 的纯度 = 翻译层质量的函数**：
- 翻译层确定性高 → "一切都是 X" 纯度高
- 翻译层概率性 → "一切都是 X" 破裂

**Pi 必须显式管理翻译失败**（/compact, /tree, /settings, ...）因为 LLM 作为翻译层不可靠。

---

## 用户的关键洞察：LLM 工作在"语义层"

**用户的理论**：
- LLM 思维 = 高层语义意图
- 底层细节 = 由大量指令/操作隐式实现
- 阻碍"一切都是 X"实现的原因 = 缺少语义意图→指令的确定性编译

**精炼为"翻译层假说"**：
> "一切都是 X"的抽象成立，当且仅当存在一个确定性的"语义→X"编译/翻译过程。当这个过程是模糊的、概率性的，或者缺失的，抽象就会破裂。

---

## 是否可能做完整翻译？

**问题**：如果限制 OS 范围（如仅 Windows），从意图 + 参数到操作指令，是否能确定性匹配？

**回答（分三档）**：

1. **封闭意图子集**（文件 I/O、构建、测试）：✓ 完全可能，MCP/结构化工具调用的做法
2. **开放意图子集**（任意编程任务）：⚠ 理论不可能，实际可近似（LLM + 约束解码 + 验证回环）
3. **完整自然语言意图**：✗ 不可能（自然语言本身开放、欠定、依赖上下文）

**Pi 的选择**：第 2 档最高灵活性版本 + 第 3 档"放弃完整性"哲学，通过 bash 直连 LLM。

---

## 用户的架构提议：分层 + 关注点分离

**核心问题**：是否能在不同层面进行完整性分析，使执行层不承担参数验证职责？

**用户的提议**：多个子系统分担职责：
- 编译层提供待执行指令
- 意图层识别意图
- 完整性分析层检测缺口
- 提示层补全缺口
- 执行层只执行已校验指令

### 五大层次

```
意图层: NL → Intent { type, semantic_params }
   ↓
完整性分析层: 必需参数清单 vs 上下文
   ↓
提示/补全层: 用户澄清缺失参数
   ↓
编译层: Intent → Instruction 序列
   ↓
执行层: 仅执行已校验指令
```

**关键原则**：执行层的契约是"给我已校验的指令"——失败不能传递给下一层。

### 这个架构的边界

**适用**：任务型意图（明确、可枚举）
**不适用**：探索型/创作型意图（"修复 bug"、"让它更好"）——这些仍需 LLM 直连

## 实现策略：扩展 pi vs 重新设计

### Pi 的扩展能力评估

**Pi 提供的扩展点**：
- `pi.registerTool()` - 注册自定义工具
- `pi.on("tool_call")` - 拦截/修改/阻塞工具调用
- `pi.on("input")` - 拦截用户输入
- `pi.on("before_agent_start")` - 注入系统提示
- `ctx.ui` - 用户交互（select, confirm, input）
- SDK（`createAgentSession`） - 程序化使用
- RPC 模式 - 子进程集成

### 推荐策略

**短期 MVP：纯扩展**
- 用扩展机制实现 60-70% 的分层效果
- 限制：无法完全约束 LLM 的工具选择自由度

**中期完整实现：SDK 重构**
- 用 SDK 自己实现 agent loop
- 在外面套上翻译层
- 保留 pi 的 provider 集成 + 工具基础设施

**长期决策点**：
- SDK 满足 → 持续优化
- 触及核心假设 → 评估 Fork
- 需要全新能力 → 重新设计

**关键判断标准**：
- 意图空间 < 100 种 → 扩展足够
- 意图空间 > 1000 种 → 需要 SDK
- 需要确定性模式 → 必须用规则表
- LLM 调用延迟敏感 → 多层 LLM 成本高

## MVP 范围讨论

**用户的提议**（基于长期 LLM 栈会大量变更的判断）：
> 短期的 MVP 核心能力应该包括：意图识别 + 基础指令 + 意图编译 + 参数补全反馈？

**精炼后的 5 大能力**：

| 能力 | 职责 | 依赖 |
|---|---|---|
| 1. 意图识别 | NL → Intent 类型 + 语义参数 | LLM |
| 2. 基础指令 Primitives | 小而正交的指令词汇 | 无 |
| 3. 上下文追踪 | 项目状态、用户历史 | 无 |
| 4. 意图编译 | Intent → Instruction 序列 | 1+2+3 |
| 5. 完整性分析 + 补全交互 | 参数缺口检测 + 用户澄清 | 4 |

### 用户提议的精炼点

**"参数补全反馈"拆为两个**：
- **完整性分析**：纯逻辑，独立可测试
- **补全交互**：UX 层，可替换

**补充"上下文追踪"**：
- 编译层需要"pattern 默认是 *.log 还是 *.{log,txt}？"——来自上下文
- 没有它，前四层无法工作

### 必须推迟的能力（不进 MVP）

- 多轮意图状态机
- 跨会话记忆
- 自动工具发现
- 微调模型替代 LLM 意图识别
- 撤销/重做（复用 pi 的 `/tree`）
- 自动学习

### 必须包含的 MVP 基础设施

1. **测试语料**（标注的真实场景 100+ 条）
2. **Schema 版本管理**（v1 → v2 迁移）
3. **可观测性**（TranslationTrace）
4. **失败模式目录**（明确"什么做不了"）
